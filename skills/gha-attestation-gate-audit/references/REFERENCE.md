# Scope, findings and false-positive boundaries

AA001 / AA002 — id-token and attestations write permissions: job permissions replace workflow-level permissions. Only literal permission declarations are checked; reusable jobs may have distinct effective permissions. AA003 — subject-name/digest pair. AA004 — implicit subject discovery is supported by newer actions/attest releases; this is a manual review flag, NOT a claim of failure. AA005 — no visible owner/repo constraint on gh attestation verify. AA006 — continue-on-error on the verification step. AA007 — simple fail-open shell suffix. AA008 — a download/release action is present but this job has no visible gh verification command. This is NOT evidence that no out-of-band verification occurs. AA009 — apparent verification before download, requiring human review of which artifact is verified.

The scanner is **not a GitHub Actions interpreter**. It does not expand expressions, simulate shell control flow, trace downloaded artifacts across jobs, follow reusable/composite workflows, inspect artifacts or validate signatures. It does not evaluate gh CLI versions or user-controlled shell aliases. It never invokes gh, git, or download actions. Only local untrusted YAML is parsed via PyYAML safe_load. No trusted-root, Sigstore or cert identity claim is made. A clean file is not a cryptographic verification result.

A proper release policy requires verification of a specific digest and signer/owner/repository identity, enforcement of its exit code and review of CI step ordering. GitHub's official docs explain both online and offline verification and repository ID nuances. Do not confuse generating an attestation with consuming or enforcing one.
