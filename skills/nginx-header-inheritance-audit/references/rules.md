# NGINX inheritance scope and rule IDs

Based on the official [ngx_http_headers_module](https://nginx.org/en/docs/http/ngx_http_headers_module.html).

- **NGH001**: security response header defined in the parent scope is absent from the effective child scope. On standard nginx behavior any local `add_header` directives replace *all* inherited `add_header` directives, even unrelated headers. `add_header_inherit off` also drops inherited headers; `merge` retains them.
- **NGH002**: local security header is missing `always`, and therefore not applied to all response status codes.
- **NGH003**: `include` references are not expanded; findings may be incomplete until all included configuration is reviewed.
- **NGH004**: invalid `add_header_inherit` mode. `on`, `off`, and `merge` are supported.
- **NGH005**: `add_header_inherit` is only present in nginx >= 1.29.3. Emitted only when --nginx-version explicitly indicates an older version.
- **NGH006**: unrecognized `add_header` shape; flagged instead of guessing behavior.

Only common security-response-header names are tracked. This tokenizer understands braces, semicolons, quotes, comments and escapes, but is **not** the nginx parser: directives generated by variables/modules, include ordering, effective virtual hosts and response-specific behavior are not resolved. Files >2MB or invalid syntax return exit 2. The report never shows header values. `add_header_inherit merge` and `off` are propagated to descendant blocks per documented inheritance semantics. For definitive behavior, run `nginx -t` and validate actual responses in staging. Do not treat static findings as a vulnerability certificate.
